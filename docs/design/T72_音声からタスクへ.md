# 音声からタスクへ — 実験的設計（意見箱 I3）

> T72（v1棚卸し）で v1 `03_design/音声からタスクへ.md` から移送（2026-09-19）。
> **未実装の設計提案**。v2で音声入力→#task化の実装痕跡は見つからず、着手時の参考として保持。
> 結論は「まず何も作らず試す（案A）」なので、実装コストは低い。

作成: 2026-08-26（夜勤 N1） ／ 対応: 意見箱 I3 ／ 前提: v1 `03_design/Slack入力プロトコル.md`（`#task` 経路が既存）

## 0. 結論（先に3行）

1. **新しい経路は要らない。** 既存の `#task` 取り込み（Slack入力プロトコル）にそのまま乗せられる。
   録音・文字化はスマホのブラウザだけで完結し、サーバーもアプリの新規開発も不要
2. **ただし Web Speech API の `continuous`（長時間・連続認識）は Android Chrome で壊れている**という報告が
   Chromium の issue tracker にある。**一次情報（issue本文）はログイン要求で本調査では確認できず、検索結果の要約のみ**（要検証）。
   これを前提に、**短い発話を都度確定させる運用**（後述）でリスクを回避する設計にした
3. **オフラインは不可。** Web Speech API は既定でサーバーベース（Google等）に音声を送信して文字化するため、
   スマホの通信は必要（Wi-Fi/モバイル回線どちらでもよい）。**PCと同一ネットワークである必要はない**という主人の制約は満たせる

## 1. 全体フロー

```
スマホ（Android Chrome）
  1. ブラウザで音声認識を開始（マイク許可は初回のみ）
  2. 話す → その場で文字に変換（サーバーに音声送信・戻りはテキストのみ）
  3. 確定した文を `#task <文字起こし>` の形にして Slack #butler へ貼る
       ↓（既存経路・変更不要）
夜のジョブ（02:00）が取り込み → 執事がタスクへ分解 → QUEUE A へ「登録してよいか」上申
       ↓
朝、主人が Slack かダッシュボードで承認 → QUEUE B / PROJECTS へ正式登録
```

`#task` 以降は Slack入力プロトコル がすでに実装済み。**本設計が新規に要るのは手順1〜3だけ**。

## 2. 手順1〜3の実装方針

### 案A: 何も作らない（推奨・最短）

Android Chrome の URL バーからアクセスできる**既存の音声入力機能**（Gboardの音声入力、
または Chrome の音声検索）で直接文字を打ち、Slackアプリに手で貼る。
**実装コストゼロ**。ただし「録音→文字化」がSlackアプリの外で起きるため、
Web Speech APIを使う理由（後述の执事管理下での文字化）がなく、単なる音声入力の代替に留まる。

### 案B: 1枚のHTMLページ（Web Speech API）を作り、スマホのホーム画面に追加

`SpeechRecognition` を使った最小ページを1つ作り、GitHub Pages 相当の静的ホスティングか
ローカルファイルとしてスマホに置く（**要検討**: 静的ホスティングは外部公開＝human_gate 判断が要る可能性がある。
ローカルファイル `file://` 起動なら公開は発生しないが、`file://` は非セキュアコンテキストとして
扱われマイクが使えない可能性が高い——**未検証**）。

ページの中身:
```html
<button onclick="start()">録音開始</button>
<textarea id="out"></textarea>
<script>
function start() {
  const r = new webkitSpeechRecognition();
  r.lang = "ja-JP";
  r.continuous = false;       // 短い発話ごとに確定させる（後述の理由）
  r.interimResults = true;    // 話している最中も表示（体感速度のため）
  r.onresult = (e) => {
    document.getElementById('out').value =
      Array.from(e.results).map(r => r[0].transcript).join('');
  };
  r.start();
}
</script>
```

**`continuous = false` にする理由**: `continuous = true` は Android Chrome で壊れているという
未確認の報告があり（§4）、リスクを避けるため。`false` でも1回の発話（数十秒程度は問題ない想定だが未検証）は
文字化できる。長い指示は「一度停止→もう一度録音開始」を繰り返す運用でカバーする。

文字化されたテキストは手動でコピーし、Slackアプリに `#task ` を先頭に付けて貼る
（**自動送信はしない**——Slack送信は執事から見て「主人の手による投稿」であり、
ページがSlackへ直接送信する経路を作ると誰の発言か・承認の起点があいまいになるため）。

### 判定

**案A（何もしない）を先に試す。** Gboardの音声入力は既にAndroidに入っており、
確認すべき論点（continuous の不具合、file://問題、公開の要否）を一切踏まずに
「音声→タスク分解→承認」の**効果（分解が実用になるか）を最短で検証できる**。
案Bは「文字化の体験を執事側で作り込みたくなった場合」の次の手として残す。

## 3. 確認済みの事実

| 項目 | 内容 | 出典 |
|---|---|---|
| ブラウザ対応 | `SpeechRecognition` は "Limited availability"（Baseline外）。Chrome for Android は Chrome 25+ で部分対応 | MDN, caniuse |
| 通信方式 | 既定はサーバーベース認識。音声はWeb service（Google等）へ送信され、テキストが返る。**オフライン不可** | MDN, Chrome for Developers Blog |
| 言語指定 | `recognition.lang = "ja-JP"` で日本語指定が可能（実装例多数で確認） | Twilio Blog（ja-jp）, Zenn記事複数 |
| 認識精度の傾向 | 一般語の認識は実用的だが、**固有名詞・専門用語は誤認識しやすい**という記述が複数の実装記事で一致 | Zenn, Twilio, note等（定量データ・WER等の数値は見つからず） |
| `continuous` の既定値 | `false`。`true` にすると発話の合間で認識を止めずに継続する仕様 | MDN |
| `processLocally`（オンデバイス処理） | 仕様上は存在するが、**実装状況はブラウザ依存で本調査では確証を得られず** | MDN |

## 4. 未確認事項（憶測で埋めていない箇所）

1. **Android Chrome で `continuous = true` が壊れているという報告**（Chromium issue #40324711）。
   検索結果の要約でしか確認できておらず、issue本文はログインが必要で読めなかった。
   現在のステータス（Fixed/Open）・具体的な症状・回避策は**未確認**。
   → 本設計は `continuous = false` 運用でこの論点自体を回避する形にしたため、実装前の追加確認は必須ではない
2. `file://` で開いたローカルHTMLファイルでマイク（`getUserMedia`）が使えるかどうかは**未検証**。
   一般に `getUserMedia` はセキュアコンテキスト必須とされるが、これは一次情報で本調査時に確認したものではない
3. 無音が続いたときの自動タイムアウト秒数（`continuous=false` でも発話後どれくらいで打ち切られるか）は
   MDN含め資料に具体的な記載がなく**未確認**
4. 日本語音声認識の定量的な精度（誤認識率等）は**データが見つからず未確認**。実運用で試すしかない
5. 案Bを実装する場合、静的ページの公開が「外部送信」に当たるかは**執事の判断だけでは決められない**
   （外部への送信・公開＝HG）。案Aで足りるならこの論点自体が発生しない

## 5. 次の一手（主人の合図があれば）

1. まず**案Aをそのまま試す**（実装不要・今すぐ可能）。Gboard音声入力→`#task `を手打ちで先頭に付けてSlack送信
2. 分解の精度・体感速度に不満が出たら案Bの実装を起票する
3. リソースを使う代替（ローカルWhisper／Cloudflare Workers AI）は意見箱I3の記載どおり、
   案A/Bで精度が足りなかった場合の次の手として温存する（GPU/メモリ確認が前提のためHG寄りの判断が必要）
