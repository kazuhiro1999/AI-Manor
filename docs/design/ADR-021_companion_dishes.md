# ADR-021: お供の提案（主菜に合わせる副菜・サラダ）

- 状態: **採択・実装済み**（2026-09-25。方針と4つの裁定 → 同日に第1段・第2段を実装。§5 に実装で決めた細部）
- 関係: ADR-018（献立のおすすめ。採点の仕組みを流用）、ADR-019（食品成分表。栄養の列を足す）、ADR-015（レシピ帳）

## 1. 何を作るか

主人の使い方: **主菜を先に決め、それに合う副菜・サラダを同時に作る**。「ラーメンのときは海藻系のサラダ」
「唐揚げや揚げ物のときはキャベツ系のサラダ」。必須ではなく、セットメニューとして
**「お供にこんなメニューはどうですか？」**と出してほしい。基準は「主菜で**足りない栄養を最も補える**もの」。

ADR-018 の `recommend` は主菜を固定すれば副菜・汁物を並べられるが、この用途では3つ足りない:

1. **物差しが粗い**: 帯は kcal・P・F・C・塩分の5項目。「海藻で食物繊維・カリウム」「キャベツでビタミンC・
   食物繊維」の違いを表せない。
2. **候補の母数**: 本番のレシピ帳は 4 件、副菜は 1 件（2026-09-25 時点）。採点しても選ぶ余地が無い。
3. **一品ものの型**: 例のラーメン・丼・炒飯は「主菜＋副菜＋汁物」の型に乗らない（本番の 4 件のうち 2 件が
   ご飯もの）。汁のある麺に汁物を勧めない、といった相性の規則も無い。

## 2. 決めたこと

### 主人の裁定（2026-09-25）
- **候補の出どころ**: 「お供の定番」を同梱する（レシピ帳の副菜と混ぜて並べる）。Claude は既定で呼ばない。
- **栄養の列**: 足す（食物繊維・カリウム・カルシウム・鉄・ビタミンC・野菜の量）。
- **主菜の入力**: **レシピ帳の主菜だけ**（レシピ帳に無い主菜を名前で選ぶ口は作らない）。
- **表示場所**: **レシピ詳細だけ**（献立ページ・XR には出さない）。

### D1 栄養の列を足す（ADR-019 D1「要るときに列を足す」の発動）
- 成分表の本表から `fiber_g`（食物繊維総量 FIB-）・`potassium_mg`（K）・`calcium_mg`（CA）・`iron_mg`（FE）・
  `vitamin_c_mg`（VITC）を取り出し、同梱 CSV・`chef_food`・`chef_recipe_meta` に列を足す。
- `veg_g`（野菜の量）は列を読むのではなく、材料のうち**食品群 06 野菜・08 きのこ・09 藻類**のグラムを足して出す。
- 出典サイトの値（`site`）を持つレシピも、**足した列だけは材料から推定**する（サイトは5項目しか載せない）。
- 帯は `[menu.band]` に**下限だけ**の行として足す（上限なし）。値は 1 日の目安の 1/3 を仮に置き、実装時に
  食事摂取基準（2025）で確かめる: 食物繊維 7 g・カリウム 900 mg・カルシウム 230 mg・鉄 2.5 mg・
  ビタミンC 33 mg・野菜 120 g（健康日本21 の 350 g/日）。
- 既知の限界: ビタミンC は加熱で減るが、名寄せは「生」を優先して引く（ADR-019 D2）ので、加熱する料理では多めに出る。

### D2 採点は ADR-018 の「逸脱がどれだけ減るか」をそのまま使う
- 主菜だけのときの不足（`deviation`）から、候補を足したあとの不足を引く。足した列も同じ式に乗る（下限だけの帯）。
- 塩分の超過は従来どおり強く減点する——ラーメン（塩分が帯を超える）に塩気の強いお供は下がる。
- 理由も定型文の符牒で返す（ADR-018 §4.1）。例: `fills_fiber_g`・`fills_vitamin_c_mg`・`pairs_with_fried`。

### D3 組み合わせの相性の規則（`lexicon.toml` の `[companion.pairing]`）
- 主菜の型（`[dish_types]` の推定）→ お供の型の加点・減点と、その理由の符牒。初期の行:
  - 揚げ物 → 生・和え物・酢の物を加点（脂っこさの口直し）
  - 汁のある麺（ラーメン・うどん・そば。焼きそば・パスタは除く）→ 汁物を出さない
  - 丼・ご飯もの → 汁物も可、野菜を加点
- **同時に作る**前提の加点: 主菜が揚げ物・煮物、または `total_minutes` が長いときは、火を使わない・レンジ・
  15 分以内のお供を加点する（コンロの取り合いを避ける）。

### D4 「お供の定番」（`src/manor/staff/chef/companions.toml`）
- 30〜50 品。1 品ごとに 題名・型（生／和え物／酢の物／汁物…）・分類（副菜／汁物）・時間・加熱（なし／レンジ／コンロ）・
  **1 人前の材料とグラム**・2〜4 行の手順。
- 栄養値は持たない——**成分表から推定して出す**（ADR-019 の `estimate_nutrition`。数字の出どころを1つにする）。
- 候補は「レシピ帳の副菜・汁物」＋「定番」。レシピ帳のものに小さく加点する（うちで作ったもの）。
  同じ料理が両方にあればレシピ帳のほうを出す（題名の突き合わせは `menu._dish_matches`）。
- 定番は「レシピ帳に入れる」でレシピに昇格できる（材料・手順をそのまま写して `chef_recipe` を作る）。

### D5 API と画面
- `GET /api/v1/kitchen/recipes/{id}/companions` → 上位 3 件（`source`: `recipe`／`catalog`・題名・理由・補う栄養）。
  主菜・ご飯もの・麺のレシピだけが対象（副菜・汁物を開いたときは空）。
- レシピ詳細の下に「お供にこんなメニューはどうですか？」のカードを 3 件。**閉じられる**（必須にしない）。
  「一緒に作る」で主菜とお供を `chef_meal` に `planned=1` で書く（既存の `POST /menu/plan`。定番は先に昇格させる）。

## 3. 段取り
1. 栄養の列（D1）: 同梱 CSV の書き出し直し → 表の列の追加 → `nutrition rebuild` → 帯に下限の行。
2. お供（D2〜D5）: 定番の TOML・相性の規則・採点・API・レシピ詳細のカード。試験は採点の表で
   （「揚げ物にキャベツが上」「汁のある麺に汁物が出ない」「塩分の超過するお供が下がる」）。

## 4. 範囲外
- レシピ帳に無い主菜（買ってきたラーメン等）を名前で選ぶ口（主人の裁定で見送り）。
- 献立ページ・XR への表示。XR で 2 品の手順を並べる「同時調理」。
- Claude に別の案を考えさせるボタン（要るとなったら第二段。既定の経路には入れない）。

## 5. 実装で決めた細部（2026-09-25）

実装: `staff/chef/companion.py`（採点は純粋関数）・`staff/chef/companions.toml`（定番 45 品）・
`lexicon.toml` の `[menu.floor]`・`[companion.*]`・`[nutrition.veg_groups]`・`web/api_v1/kitchen.py`（4つの口）・
`web/src/modules/kitchen/CompanionPanel.tsx`。試験は `tests/staff/test_chef_companion.py`（主人の例を表に）・
`test_chef_nutrition_micro.py`・`tests/web/test_kitchen_companions.py`・`Companion.test.tsx`。

### 5.1 下限は `[menu.band]` ではなく `[menu.floor]` に置いた（D1 の言い換え）
帯は `[下限, 上限]` の組で、上限の無い項目を書けない（TOML に「無し」が無い）。下限だけの節を分けた。
**献立のおすすめ（`recommend`）はまだ下限を見ない**——表示先を裁定どおりレシピ詳細だけにしたので、
献立ページの採点を変えるのは要るとなってから（`menu.py` は触っていない）。

### 5.2 「分からない」は 0 と読まない
足した5項目の解決率（`micro_coverage`）が `[companion.rules].micro_coverage_min`（0.6）を下回る主菜は
下限の項を丸ごと見ず、候補は「補える」と言わない。成分表の空欄も 0 と読まない（混ぜ物も空になる）。

### 5.3 型・加熱・印はうちのレシピからも推定する
定番は `kind`・`heat`・`tags` を明示。うちのレシピは題名（`[dish_types]`）・工程の文（`[companion.heat_cues]`）・
材料（`[companion.tag_cues]`）から推定する。題名に型の語が無い副菜は、火を使わなければ「生」とみなす
——「塩昆布の無限キャベツ」がこれで揚げ物の相性に乗る。

### 5.4 塩分の警告はお供自身が控えめでないときだけ
ラーメン・丼のように主菜だけで帯を超えるとき、どのお供でも合計は超えたままなので、全部に警告が付くと
何も言っていないのと同じになる。上限の 1/4 以下のお供には「塩分控えめ」を出し、警告は出さない。

### 5.5 定番は「一緒に作る」だけならレシピ帳に入れない
`chef_meal` は題名と材料しか持たないので、定番のまま記録できる。気に入ったら「レシピ帳に入れる」
（同じ題名が既にあればそれを返す。入れた後は定番ではなくうちのレシピとして並ぶ）。

### 5.6 閉じた状態はこの端末に覚える
「閉じる」は `localStorage` に置く（端末ごと。読めない環境では開いたまま）。サーバには持たない——
家族の誰かが閉じても、他の人の画面からは消えない。

### 5.7 本番への入れ方
`uv run manor init`（列の追加と、成分表の足した列の1回だけの埋め直し）→ `uv run manor web build`
→ サーバの再起動。

## 6. 定番の作り方はレシピサイトから引用する（2026-09-25 午後。§2 D4・§5.5 の改め）

主人「お供のレシピは、基本的に AI 生成ではなくどこかのレシピサイトにあるものを引用したい。
今の仮レシピに合う一般的なレシピをサイトから探して候補として入れてほしい。取り込むかは私が見て決める」。

### D8 定番は「料理の型」、作り方はサイトの候補
- `companions.toml` から**手順を消した**。残る材料とグラムは**栄養の目安のためだけ**の一般的な分量
  （特定のレシピの引用ではない、とファイルの頭に明記）。手順を消しても推定値は1品も変わらない（実測）。
- 作り方の候補は `companion_sources.toml` に定番ごとに 2〜3 件。持つのは **URL・サイト名・題名・画像の直リンク・
  目安の時間・選んだ理由**だけ（本文や材料は写さない——レシピ帳の取り込みと同じく、取り込むのは主人が選んだときだけ）。
- 候補は検索で集め、各 URL を manor の取り込み（自動抽出）に通して材料と手順が読めることを確かめた。
  サイトは クラシル・白ごはん.com・DELISH KITCHEN・Nadia を優先（取り込みのアダプタがあるサイト）。

### D9 画面と取り込み
- 定番のカードは「レシピサイトの候補（N）」を開くと、候補ごとに「サイトで見る」（新しいタブ）と
  「レシピ帳に入れる」を出す。後者は `/kitchen/recipes/new?url=…` を開き、**自動抽出まで進めて止まる**
  ——下書きを見て「登録」を押すのは主人（ADR-015 の取り込みと同じ画面・同じ確かめ方）。
- 定番の写真は候補の先頭の画像を借りる。
- **§5.5 の「レシピ帳に入れる」（AI の手順を写して昇格）と定番の作り方の口（`GET /kitchen/companions/{key}`・
  `POST …/adopt`）は廃止**した。
- 候補の URL を取り込んだレシピがレシピ帳にあれば（出典 URL を大小・末尾の `/`・クエリを無視して突き合わせる）、
  その定番は出さない——取り込んだものが「うちのレシピ」として代わりに並ぶ。使うほど定番が本物に置き換わる。
- 「今夜一緒に作る」は定番のまま記録できる（従来どおり）。
