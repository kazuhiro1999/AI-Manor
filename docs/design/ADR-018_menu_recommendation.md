# ADR-018: 献立のおすすめ（レコメンデーション）

- 状態: **採択**（2026-09-13。第一段 D7-1「規則だけ」を実装して採択。§4 に実装で決めた細部）
- 調査: `docs/reports/2026-09-13_menu-planning-research.md`
- 関係: ADR-015（レシピ帳。3 軸・栄養値）、`chef_pantry`（在庫）、`chef_meal`（食事の記録）、`chef_taste`（好み）

## 1. 何を作るか

「献立を決めてくれる」ではなく、**レシピ帳から複数の候補を理由つきで並べる**レコメンデーション。
ユーザーの言葉: 「おすすめ 1 つではなく、複数を理由付きで。例えば『1 位 きゅうりとわかめの酢の物 — 海藻類で
塩分摂取を抑制』のような感じ」「主菜も提案できたほうがいい」「人数や気分を入れると、それらを考慮した
おすすめが並ぶ」「在庫は制約にせず、あればそれを使うレシピを上位に載せる」。

## 2. 決めたこと

### D1 対象は栄養値のあるレシピだけ
`chef_recipe_meta` の kcal・たんぱく質・脂質・炭水化物・塩分が揃っているレシピだけを候補にする。
栄養値の推定（材料から埋める・知識ベースから引く）は**この ADR の範囲外**（レシピデータの整備として別に行う）。
候補から外れたレシピは、Web の一覧で「栄養値なし（おすすめの対象外）」と分かるようにする。

### D2 1 食の帯（採点の物差し）
1 食あたりの目安の範囲。食事摂取基準（2025）と食事バランスガイドから 1 日の 1/3 として置く:
kcal 600〜900、たんぱく質 20〜35 g、脂質 15〜30 g、炭水化物 75〜130 g、塩分 2.5 g 以下。
**`lexicon.toml` の `[menu.band]` に置き、ユーザーが書き換えられる**（体格・方針で変わるため）。
帯は「1 人前」の値。人数は分量の表示にだけ効き、採点には効かない。

### D3 入力と出力（レコメンデーションの形）
- 入力: `main_recipe_id`（省略可。主菜が決まっているとき）、`people`（既定 2）、`mood`（自由文。省略可）、
  `slot`（`dinner` 等。省略時 `dinner`）、`exclude`（除外するレシピ id）。
- 出力: **枠ごと**（主菜・副菜・汁物）に候補を採点順で最大 5 件。各候補は `recipe_id`・`title`・`score`・
  `reasons[]`（短い日本語の理由。1〜3 個）・`nutrition`。加えて「主菜 + 副菜 1 位 + 汁物 1 位」の**組み合わせ
  の合計**と帯との比較（`band_check`: 各項目が 帯内／不足／超過）。主菜が未指定なら主菜の枠も並べる。
- 理由は**規則が出す定型文**（「海藻で塩分を抑える」「在庫のほうれん草を使う」「主菜と調理法が被らない」
  「先週は作っていない」「10 分で出来る」）。LLM で書かせない（D5）。

### D4 採点（規則。重みは `lexicon.toml` の `[menu.weights]`）
| 因子 | 何を見るか | 例の理由 |
|---|---|---|
| 帯への寄与 | 主菜と合わせたときに合計が帯に近づくか（塩分は超えると強く減点） | 「塩分を抑える」「たんぱく質を補う」 |
| 多様性 | 主菜と 素材・ジャンル・調理法（`dish_types` から推定）が被らない | 「主菜が肉なので野菜を足す」 |
| 在庫 | `chef_pantry` にある材料を使う（**加点のみ。無くても減点しない**。期限が近ければ加点を増やす） | 「在庫のほうれん草を使う」 |
| 履歴 | `chef_meal` で直近 7 日に出た料理は減点 | 「今週はまだ作っていない」 |
| 好み | `chef_taste`（嫌い・避ける食材は除外、好きは加点） | — |
| 時間 | `total_minutes` が短いものを副菜・汁物では加点 | 「10 分で出来る」 |
| 評価・回数 | `rating`・`times_cooked`（作り慣れたものを少し上に） | 「よく作る」 |

在庫は「あるか無いか」だけを見る（量は見ない）。登録漏れ・使い忘れがあっても結果は「少し順位が違う」だけで
壊れない——これが「制約にしない」の意味。

### D5 LLM の線引き
- 使う: `mood` の自由文（「さっぱりしたもの」「がっつり」「子どもがいる」）→ 条件の JSON（ジャンル・味・
  時間・避ける素材）への翻訳だけ。`claude -p`（haiku・JSON のみ・5 秒）。失敗したら mood を無視して続ける。
- 使わない: 栄養計算・在庫判定・候補の網羅・採点・最終決定・理由文。既定の経路に LLM を入れない（ADR-015 D7 と同じ理由）。
- 第一段では mood は**語彙の一致だけ**（`lexicon.toml` の `[menu.mood]` にキーワード → 条件）。LLM は第二段。

### D6 API と画面
- `GET /api/v1/kitchen/menu/recommend?main_recipe_id=&people=&mood=&slot=&exclude=` → D3 の形。
- 料理長 Web の別ページ **`/kitchen/menu`「今日のおすすめ」**: 上に 人数・気分（チップ＋自由文）・主菜（レシピ帳から選ぶ／おまかせ）、
  下に 枠ごとの候補（題名・理由・kcal と塩分・写真）と「この組み合わせ」の帯との比較。候補を押すとレシピの詳細へ。
  「この献立にする」で `chef_meal` に `planned=1` で 3 行書く（履歴の減点に使う）。
- XR は当面読まない（Web で決めてからレシピを選ぶ）。

### D7 段取り
1. 規則だけ: `[menu.band]`・`[menu.weights]`・`[menu.mood]` を `lexicon.toml` に足し、`staff/chef/menu.py`（純粋関数の採点）＋ API ＋ 頁。試験は採点の表で。
2. mood の LLM 翻訳（`claude -p`）を選べる後ろ盾として。
3. 在庫の入力経路の改善（買い物リストの「買った」→ 在庫へ）。

## 3. 範囲外（別の作業）
- 栄養値の無いレシピの推定（食品成分表の取り込みはここで行う）。
- 週間の献立表・買い物リストの自動生成（第一段の結果が使えると分かってから）。

## 4. 実装で決めた細部（第一段 D7-1。2026-09-13）

実装は `src/manor/staff/chef/menu.py`（採点は純粋関数）・`src/manor/staff/chef/lexicon.toml`
の `[menu.*]`（数値の唯一の出どころ）・`src/manor/web/api_v1/kitchen.py`（2つの口）・
`web/src/modules/kitchen/MenuPage.tsx`（`/kitchen/menu`）・`manor chef menu`。

### 4.1 理由は「定型文の符牒」で返す（D3 の言い換え）
D3 は理由を「短い日本語の定型文」と書いたが、Web は ja/en の2言語を出す（ADR-012）ので、
サーバが日本語の文を組むと英語の画面に日本語が出る。よって API が返すのは
`{"code": "fills_protein_g", "params": {...}}` の形にし、文へ直すのは表示側
（CLI は `chef.menu.reason.*`、Web は `kitchen.menu.reason.*`）に置いた。
**定型文であること（LLM に書かせない。D5）は変わらない。**

### 4.2 帯への寄与は「相対逸脱がどれだけ減るか」
項目ごとに `不足 = (下限 - 値) / 下限`、`超過 = (値 - 上限) / 上限` を採り、`band_<項目>` の
重みを掛けて足す。相対量にしたのは kcal（数百）と塩分（数 g）を同じ物差しで足すため。
候補の点は「主菜だけの逸脱 − 主菜＋候補の逸脱」＝**逸脱がどれだけ減ったか**に `band`（2.0）を
掛けた値。塩分の超過だけ `salt_over`（2.0）を上乗せする（D4「強く減点」）。
帯の中に既に収まっているときは寄与が小さくなる——そのときは在庫・気分・多様性が順位を
決めてよいという判断（重みの初期値は `[menu.weights]` のコメントに理由つきで書いた）。

### 4.3 ジャンルは「揃う」ほうを小さく加点（D4 からの修正）
D4 は多様性の因子に「素材・ジャンル・調理法が被らない」と書いたが、そのまま実装すると
和食の主菜にエスニックの副菜を勧める。調査報告 §3.4 の「ジャンルの許容表」の趣旨に合わせ、
**素材（0.5）と調理法（0.4）は被らないほうを加点・ジャンル（0.15）は揃うほうを小さく加点**にした。

### 4.4 主菜の枠では多様性を採らない
主菜を提案するときは比べる相手がいないので、多様性の項も時間の加点も出さない。
主菜同士の代わり映えは**履歴の減点（1.0）と評価・回数**で付ける（ユーザーの裁定どおり）。

### 4.5 献立は共通（`viewing_user_id` は絞りに使わない）
動画リスト（ADR-016 D1）は利用者ごとにしたが、献立は**食卓が1つ**なので共通にする
（ADR-014 D4「台所は共通」）。両方の口は `viewing_user_id` を解決して応答の
`viewing_user_id` に載せるが、候補の絞りには使わない——誰が開いても同じおすすめが出て、
誰が決めた献立も同じ履歴に効く。試験（`tests/web/test_kitchen_menu.py`）でこれを固定した。

### 4.6 `slot` と `people` は採点に効かない（第一段）
`people` は D2 のとおり分量の表示にだけ効く（採点は 1 人前の帯で行う）。`slot`（dinner 等）は
`plan` の書き込み先を決めるだけで、朝・昼・夜で帯や重みは変えない——変えたくなったら
`[menu.band]` を枠ごとに分ける（今は1つ）。

### 4.7 `[menu.rules]` と `[menu.slots]` を足した
D2・D4 が挙げた帯・重み・気分のほかに、**閾値**（`top_n` 5・`history_days` 7・
`quick_minutes` 15・`expiring_days` 3・`pantry_items_max` 3・`reasons_max` 3）と
**枠 → `category` の対応**（`main`=主菜／`side`=副菜／`soup`=汁物）も `lexicon.toml` に置いた。
`menu.py` に日本語の分類名と数値を1つも持たせないため（ADR-002 §3「語彙の出どころは
lexicon.toml だけ」）。

### 4.8 気分は絞り込みではなく加減点
`[menu.mood]` の節（さっぱり／がっつり／早く／温かい／野菜／魚）に `keywords`（言い換え）と
条件（`cuisine`・`main_ingredient`・`dish_types`・`exclude_dish_types`・`max_minutes`）を持つ。
自由文にキーワードが含まれたら条件が効くが、**合わないものを候補から外さない**
（`mood_match` 0.5 の加点／`mood_mismatch` 0.5 の減点）——気分に合う候補が 0 件のときに
画面が空になるより、合うものが上に来るだけのほうが使える。在庫と同じ姿勢（D4）。

### 4.9 献立の保存先は `chef_meal`（論点3への答え）
`chef_menu_plan` は作らない。`chef_meal` に `planned=1` で 1 品 1 行を書く——**書いたそばから
履歴の減点に効く**（D4 の「履歴」は `chef_meal` を見る）のが利点。`chef_meal` は `recipe_id` を
持たないので、題名（`dish`）と材料（読点区切り）を写して書き、履歴の突き合わせは題名で行う
（`ops.item_match` は材料名向けに緩すぎるので、題名は「どちらかがどちらかを含む」だけで見る）。
`recipe_id` 列を足すのは ADR-015 D5 が保留にしたままで、第三段の課題。

### 4.10 主菜に栄養値が無くても拒まない
D1 は**候補**を絞る規則なので、主人が明示した主菜は栄養値が無くても受ける（帯への寄与を
「主菜 0」として数え、多様性と気分だけが効く）。画面は「栄養値なし」と出す。

### 4.11 状態コード
`ERR_BAD_REQUEST`（語彙外・範囲外・`recipe_ids` が空・日付の形式）→ 400、
`ERR_RECIPE_NOT_FOUND` → 404。写し先は `web/api_v1/kitchen.py` の `_menu_error_to_http`
1か所（ADR-016 の `_media_error_to_http` と同じ流儀）。`plan` は1品でも見つからなければ
何も書かない（例外で 1 トランザクションごと巻き戻す）。

## 5. 使い方の前提（2026-09-13 ユーザー）

- 使うのは**夕食と、土日の昼食**。毎回ではない（外食もある）。朝食は残り物や決まったパン・ご飯で、明示的に
  登録しない限り記録に載らない。
- したがって **1 日の合計は計算しない**（帯は 1 食で閉じる。D2）。履歴の減点（D4）は `chef_meal` に**記録のある
  食事だけ**を見る——記録が無い日があっても結果は「少し順位が違う」だけで壊れない。既定の枠は `dinner`。
- **お弁当の作り置き**（1 週間分を週末に一気に作る）は別の問い。要る印は 日持ち（冷蔵の日数）・冷凍可・
  冷めても美味しい（弁当向き）で、今のレシピ帳には無い。ユーザーは来月から始める予定で**素案段階**——
  実際に作るようになってから相談し、必要なら第二段として ADR を足す。今は設計に入れない。
