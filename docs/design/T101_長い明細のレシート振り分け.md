# T101: 明細が長いレシートの振り分け（実測と結論）

## 問い

「長い明細のレシートは、OCR を飛ばして先に Claude に読ませたほうがよいか」
（`receipt quick` で行数を数え、20行を超えそうなら Claude 直行、という案が `now` にあった）

## 実測（2026-09-26。`home/receipts` の実物5枚。②のため中身は出さない・件数のみ）

| 画像 | full OCR 箱数 | quick OCR 箱数 | OCRのみ(allow_claude=False)の判定 | 明細数 |
|---|---:|---:|---|---:|
| A | 125 | 119 | needs_review | 25 |
| B | 73 | 71 | ok | 18 |
| C | 43 | 39 | ok | 3 |
| D | 39 | 35 | ok | 2 |
| E | 71 | 71 | ok | 8 |

`quick` モデル（`receipt quick` が使うもの）の箱数は `full` モデルとほぼ一致する
（A: 119 vs 125、B: 71 vs 73）ので、撮影直後の簡易チェックでも同じ傾向は見える。

**Aだけ**（明細25件・最多）が OCR のみでは `needs_review`。18件（B）は OCR のみで `ok`。
「20行くらいが境目」という当初の勘は、この1件に関しては合っている。

## 実際に Claude 込みで読ませた結果（A・実機1回）

`allow_claude=True`（既定）で A を読み直すと:

```
review=ok  method=ocr+claude  attempts=[ocr, ocr+claude]  elapsed=26.2s
```

**既存のパイプラインは、OCR が `needs_review` のときに自動で Claude へ回して
`ok` まで持っていける。** つまり「長いレシートが正しく読めない」という問題は
**現状のコードで既に解決している**（`receipts.read_image` のフォールバック＋
`_score` によるベスト選択）。

## 結論

`now`/`next` にあった「行数を数えて Claude 直行に振り分ける」は、**正しさのためには不要**
（フォールバックが既に正しさを保証している）。得られるのは**レイテンシだけ**——
Aの26.2秒のうち OCR 単体は数秒（実測3.9秒）なので、先読みで省ける時間は 1〜2 割程度。

見送りの理由:
- 実物の「長い」サンプルが1枚しかなく、閾値（箱数何個で振り分けるか）を実データで
  詰められる状況にない。1枚だけで固定した閾値は、逆方向の誤判定（本来 OCR で読める
  短いレシートを Claude 直行にしてしまう＝無駄な呼び出しが増える）の実害が読めない
- 得られる効果（数秒のレイテンシ短縮）に対して、誤判定のリスクとコードの複雑化が見合わない

**T101 は「読めない」という意味では解決済みとして閉じる。** 再燃条件: 実際に長い
レシートの読み取りが体感で遅い・失敗する、という報告が主人からあったとき（そのときは
サンプルも増えているはずなので、閾値をまともに詰められる）。
