# レシート読み取り: 「OCR 先」と「最初から Claude の目」の実測比較

作成: 2026-09-24 ／ 実測: 執事 ／ 対象: `home/receipts` の実物 4 枚
／ 立ち位置: **③ナレッジ層（参考情報）**。ADR-020 D1 の判断が今も妥当かを、手元の実データで確かめたもの
／ 主人からの問い: 「今は Claude は取りこぼし・失敗した場合のみ起動して修整する形か。最初から Claude の
vision で認識する場合と比べて、処理時間・消費トークン・読み取り精度にどのくらい差があるか」

## 1. 答え（要約）

- **いまの形はその理解で合っている。** 既定は「前処理 → ローカル OCR → 規則 → 検算 6 本」で、
  Claude を呼ぶのは**検算に落ちたとき**と**初めて見る品名の分類**だけ（ADR-020 D1）。
- **精度**: 4 枚中 3 枚は同点（どちらも検算が通る）。差が出たのは明細 31 行のロピアだけで、
  **Claude の目のほうが正しい**（31 品を取り、検算も通る。OCR は 25 品で検算に落ちる）。
- **時間**: OCR は 1 枚 **3.3〜6.3 秒**、Claude は **6.5〜20.0 秒**。**OCR が 2〜3 倍速い**。
- **費用**: Claude は 1 枚 **$0.027〜0.047**（API 換算。Max プランでは定額の内側）。OCR は 0。
  毎日 1 枚で月 **$0.8〜1.4**、月 100 枚なら **$2.7〜4.7** 相当。
- **結論**: 「OCR 先・Claude は後ろ盾」は今も妥当。ただし**長いレシートでは Claude のほうが強い**ので、
  §4 の折衷（行数で先に振り分ける）を検討する価値がある。

## 2. 測り方

同じ 4 枚に対し、同じ前処理（傾き補正・リサイズ）を通したあと:

| 経路 | 中身 |
|---|---|
| **OCR 先**（いまの形） | RapidOCR（PP-OCRv6 small・CPU）→ `receipt_parse` の規則 → `receipt_checks` の検算 6 本 |
| **Claude の目** | 同じ前処理の画像を縦 2 分割して `claude -p`（Sonnet・思考なし・1 ターン）へ。**OCR の文字列は渡さない**（純粋に目だけ） |

正解は DB の `committed` の値（主人が手で直したものを含む）。どちらの経路も DB には書いていない。
⚠ **この日の午後に OCR 側の穴を 5 つ塞いだあとの計測**（桁落ち・軽減税率の印・カード控え・
レジの誤検出・合計の字。CHANGELOG 2026-09-24 その3）。塞ぐ前は 4 枚中 1 枚（ファミマ）が
OCR では読めなかった。

## 3. 実測

| # | 店 | 明細 | 正解 | OCR 先 | Claude の目 |
|---|---|--:|--:|---|---|
| 1 | ロピア | 31 行 | 12,308 円 | 12,308 円 / **25 品** / ⚠検算に落ちる / **6.3 s** / 0 円 | 12,308 円 / **31 品** / ✓ / 20.0 s / $0.0469 |
| 2 | 魚べい | 18 行 | 4,620 円 | 4,620 円 / 18 品 / ✓ / **3.6 s** / 0 円 | 4,620 円 / 18 品 / ✓ / 11.5 s / $0.0352 |
| 3 | キャッツカフェ | 3 行 | 2,822 円 | 2,822 円 / 3 品 / ✓ / **3.3 s** / 0 円 | 2,822 円 / 3 品 / ✓ / 9.1 s / $0.0276 |
| 4 | ファミマ | 2 行 | 369 円 | 369 円 / 2 品 / ✓ / **3.7 s** / 0 円 | 369 円 / 2 品 / ✓ / 6.5 s / $0.0265 |
| | | | **合計** | **16.9 s** / 0 円 | **47.1 s** / **$0.136** |

- **合計金額はどちらも 4 枚とも正解。** 差が出るのは明細の行数。
- **Claude の時間は画像の大きさではなく明細の行数で伸びる**（出力する JSON が長くなるため。
  2 品 6.5 s → 31 品 20.0 s）。費用も同じ傾向（$0.027 → $0.047）。
- **OCR の時間はほぼ一定**（3〜6 秒。CPU・PP-OCRv6 small）。GPU なら 2026-09-22 の調査で 6〜7 秒 →
  ここでは CPU でも速いのは、前処理後の画素が調査時より小さいため。

### いまの形での実際の挙動（#1 の場合）

OCR が検算に落ちる → **自動で Claude が読み直す** → 検算が通る → 登録。
つまり #1 は結果として「OCR 6.3 s ＋ Claude 20.0 s ＋ $0.047」かかっており、
**最初から Claude に投げるより遅く・同じ費用**。逆に #2〜#4 は Claude を呼ばないので
**0 円・3〜4 秒**で済む。

## 4. 含意（どちらが良いか）

**枚数の大半が短いレシート（コンビニ・スーパー）なら、いまの形が正しい。** 4 枚のうち 3 枚が
0 円・3〜4 秒で片付き、長い 1 枚だけ後ろ盾を使う。1 枚あたりの平均は 0.034 ドル → **0.012 ドル**に下がる。

一方、**明細が 20 行を超えるレシートは OCR の規則では落ちやすい**（行の詰まり・傾き・
価格と品名の対応）。#1 は今日 5 つの穴を塞いだあとでも 25/31 行しか取れていない。
この帯では「先に Claude」のほうが**速くて安い**（二度手間にならない）。

**折衷案（未実装）**: 簡易チェック（撮影直後の `receipt quick`）で紙の高さ・行らしき帯の本数を数え、
**20 行を超えそうなら OCR を飛ばして Claude から**読む。短いものは従来どおり OCR だけ。
→ T101 として起票。

### 変えないほうがよい理由（ADR-020 D1 の趣旨）

- **Claude が呼べなくても登録が完了する**ことが設計の柱。2026-09-24 に実際に認証が切れ、
  Claude が丸一日使えなかったが、短いレシートは OCR だけで通った。
  「最初から Claude」にすると、この日は**1 枚も読めなかった**。
- 費用は定額の内側だが、**呼ばない経路があること自体が保険**になっている。
