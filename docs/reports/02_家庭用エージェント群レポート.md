# 家庭用エージェント群レポート

作成: 2026-09-02／対象: `manor`（AI執事 v2）の部下4名（chef / housekeeper / steward / secretary）
＋ v1 から継承した検分役（qa）・監査役（auditor）。ROADMAP.md ゴール②の成果物。

## 1. 要約

執事の下に、家庭で繰り返し発生する4領域を担当する部下を作った: 料理長 `chef`・家政婦
`housekeeper`・家令 `steward`・秘書 `secretary`。各担当は定義（`.claude/agents/*.md`）・専用の
SQLite 表・Python 製 CLI（`manor <group> ...`）・試験一式を持つ。試験は4名合計156件、リポジトリ
全体で319件が緑・1件 skip（実測）。執事は `manor handoff new` で指示書を生成して委譲し、報告を検分
（`accept`/`reject`）してから主人へ渡す。v1 から検分役 `qa`・監査役 `auditor` の定義も移植済み。

## 2. なぜこの4人か

判定基準は外部レビュー提案6・ADR-002 §1 が採る「**繰り返し出てくる、完結した推論を持つ領域**」。
家庭で毎日〜毎週繰り返し、他の領域を知らなくても判断が閉じるものを4つに切った。

独立させなかったもの:

| 候補 | 置き場 | 独立させる条件 |
|---|---|---|
| 健康 | `chef` の週次振り返り（食事の偏り）に含める | 同じ相談が3回来てから（ADR-002 §1） |
| 司書（知見の整理） | `secretary` の inbox 仕分けに含める | 同上 |

外部レビュー提案6の根拠: 「専門化は完結した推論を持つときに効く。文脈を LLM 境界で分断する
ときには効かない」（Atlassian の知見として同文書に記録）。一度きりの実務にまで担当を増やすと、
担当の数だけ委譲コストが増える。

| `housekeeper` | 家政婦 | いつ何を手入れするか | 修理の実行、業者の手配 | `housekeeper_chore/_chore_log/supply/maintenance/waste`（5） | `manor house` |

## 4. 全員に共通の設計（ADR-002 §2・ADR-001 §11）

- **プラグイン規約**: `src/manor/staff/<name>/{__init__.py, schema.sql, cli.py, ops.py}` を1セット
  置くだけでよい。core の `cli.py` が `importlib`/`pkgutil` で列挙し `register(subparsers)` を呼ぶ
  （`src/manor/cli.py` で確認）。レジストリの手編集は不要
- **道具は判断しない**: 並べ替え・突き合わせ・集計・期日計算まで。何を勧めるかは担当（LLM）
- **自分の表にしか書かない**。core の表は読むだけ。唯一の例外は `housekeeper supply low
  --to-shopping` が `chef_shopping` へ書くこと（ADR-002 §4）
- **外部送信しない**。主人にしか決められないことは**執事へ**（`manor decision ask`）
- **相対日付は道具が解く**: `secretary` の `resolve-date` が絶対日付の唯一の出どころ。他担当の
  CLI は `YYYY-MM-DD` のみを受ける
- **人格**: ですます調・短く・落ち着いて。**媚びない**（一度は申し上げ、述べたら主人の選んだもの
  を支える）

## 6. qa と auditor（v1 から継承）

`qa` は**成果物**を検める。実行できるものは実行して確かめ、できないものは「確かめていない」と
書く。直さない（誤字・壊れたリンクを除く。除いた場合も報告に書く）。`auditor` は**執事自身の
規則**（①層: `CLAUDE.md`／`butler/*.md`／`.claude/{rules,skills,agents}/`／`.claude/settings.json`）
だけを読み、月1回まっさらな文脈で監査する。両者とも `home/` 配下**全部**を読まない（v1 の
`agents/*/data/` に相当する境界を継承。「報告に写さない」より前に「読まない」で守る）。`auditor`
はさらに `src/` の実装を読まない（動作の当否は `qa` の担当）。

## 7. 執事との連携

`manor handoff new <task> --to <agent> --scope ".." --verify ".." --mode read|write` が DB から
指示書を組み立てる。生成される見出しは10個（`src/manor/handoff.py` で確認）: 役割とスコープ／
背景／目的 / 今の状態 / 次の一手／Project Policy／制約／関連（グラフから）／成果物と置き場／
検証要件／定型／報告の型。

報告（`manor handoff report`）は5見出しを必須とし、欠けていれば終了コード1で拒否される:
`## やったこと` `## 証跡` `## やっていないこと` `## 曖昧だった点` `## 主人にしか決められないこと`
（空なら「なし」）。`accept` は owner を butler に戻す。`reject` は理由が必須で、owner を butler
に戻したうえで status を `hold` に置く（次に誰へ渡すかは執事が決める。実装で確認）。

**架空の例**（「今夜の献立」を chef へ委譲）: ①`manor handoff new T99 --to chef --scope
"chef_pantry,chef_meal,chef_shopping" --verify "献立案3つ以内、推し1つ明示" --mode write` で指示書
生成 ②Agent ツールへ貼って起動 ③chef が `pantry list`→`taste show`→`pantry expiring --days 3` を
見て候補3つ・推し1つを提案し `meal log --planned` で仮記録 ④5見出しの報告を `handoff report` で
登録 ⑤執事が検分し、アレルギー表記に不足が無ければ `accept`。あれば `reject --note "卵アレルギー
の注記が無い"` で差し戻す（status は `hold`）。

### 7-2. 主人 → 担当の直接対話（2026-09-02 追加）

執事を通さず担当と話す経路は `uv run manor talk chef`（実体は Claude Code の `claude --agent chef`。
担当の定義がそのまま人格・道具・モデルになる）。`CLAUDE.md` に「担当として起動されたとき」の節があり、
担当は執事の仕事（起票・裁定・委譲）をせず、自分の表にだけ書く。DB は執事と共有なので、
料理長が書いた在庫は執事にもダッシュボード（`manor board` の「家」画面）にもそのまま見える。詳細は `docs/talk.md`。

## 9. 設計で見つかった曖昧点と裁定（ADR-002 §9 の要約）

| 担当 | 曖昧だった点 | 裁定 |
|---|---|---|
| chef | `pantry expiring` は全在庫か `--days` 以内か | `--days` 以内＋期限不明は常に含める（安全側） |
| chef | 終了コード2は「表が空」か「絞り込み0件」か | 表が空のときだけ2。絞り込み0件は正常 |
| housekeeper | `threshold` は「下回る」か「以下」か | 以下（`qty <= threshold`）に統一 |
| housekeeper | 過去日の `done` で `last_done` が巻き戻るか | 巻き戻らない（新しい方を保つ） |
| steward | `trend` に取引の無い月をどう出すか | データのある月だけを対象（0円の月を捏造しない） |
| steward | 並び順の細則 | 超過差順→予算内残り少ない順→予算未設定は名前順 |
| secretary | `agenda` の「期間内」と「超過」の扱い | 下限なし・上限のみ。超過は先頭 |
| secretary | `M/D` が2/29で当年が平年のとき | `ManorError`（次の閏年まで探さない） |

**なぜ毎回指摘させるのか**: v1 の改善サイクルの知見による。実装報告の曖昧点指摘は「エージェント
自身の指摘——ここが一番濃い」（v1 `改善サイクル.md`）とされ、改善の種として最も具体的な情報源
だった。v2 でも `manor handoff new` の「定型」節に同じ一行が固定で入っている（ADR-001 §8）。
