## 2. v1 の何が問題だったか

### 外部レビューの総評

外部レビュー`../AI執事レビュー_2026-08/02_レビューと改善提案.md`（v1ワークスペース外・読み取り専用参照元）§0 は次のように結論している。

> 「やり方は正しい。世の中の到達点と比べても上位にある。直すべきは『構造』ではなく『重さ』。」

具体的には、起動時に読むと定められたファイル群が合計約178KB（約5〜6万トークン）に達し、その過半が `tasks/QUEUE.md`（当時125KB、うち77%は完了済み履歴）だった。同レビューは hooks を「散文の規則を機構に変える最大の未使用資源」と名指しし（提案4）、CLAUDE.md のダイエット（提案2）・射影化（提案1）・外部監査枠の新設（提案5）を挙げている。

### 主人の要望（意見箱、原文引用）

| # | 要望 |
|---|------|
| I6 | 「進行中ステータスが、進捗が分かりづらい。例えば論文修正の4件は、ほぼ完了の状態と、今から（実装中）が同じステータスになっていて違和感。」 |
| I8 | 「タスク管理に関しては肥大化する前にデータベース連携や更新時のパイプライン、インターフェース、プロトコルを整備した方が事故が少なく済みそう」 |

### v1 自身の分析

`03_design/タスクデータをDBにする.md` §1 は、2026-08-27の1日で見つかった不整合15件を「SQLiteなら構造的に起きないか」で分類し、**8件が構造的に消える**と結論している（残り7件は語彙選択や実行環境の問題で、DB化とは無関係）。同文書はこの時点で「DB化は段2（突き合わせ）止まり。書き込みは依然としてMarkdown直編集」（意見箱 I8 の指摘と一致）と記録している。

## 3. 改善点

### 3.1 SQLite が唯一の書き手、Markdown は射影

**何を変えたか**: `home/manor.db` だけが真実になった。`home/projections/*.md`・`home/STATE.md` は `manor render` が書き出す生成物で、`.claude/settings.json` の `PreToolUse` hook（matcher: `Edit|Write|MultiEdit`）が対象パスへの直接編集を deny する。

**なぜか**: v1 は段2（突き合わせ）で止まっており、書き込みは今もMarkdown直編集のまま（意見箱 I8）。ADR-001 D1 は「双方向同期はしない。片方が正か分からなくなる」と決めた。

**根拠**: v1 の不整合8類型それぞれに、それを再現しようとして失敗する試験が1本ずつある。

| # | v1 で起きたこと | v2 で起きない理由 | 試験 |
|---|---|---|---|
| ① | ブロッカーが片付いたのに待っている | 依存が `edge` の行。`v_blocked_ready` が拾う（decision も見る） | `test_v1_class_1_blocker_cleared_but_waiting` |
| ② | 進行中のまま何日も記録が無い | `task_event.at` がある。`v_stale_doing` | `test_v1_class_2_doing_with_no_activity_for_days` |
| ③ | sed の過剰一致で隣の行が壊れた | 更新は id 指定。隣に当たらない | `test_v1_class_3_id_scoped_update_no_collateral_damage` |
| ④ | 見出しに書いた状態が古い | 状態の列は1つ | `test_v1_class_4_single_status_column_no_stale_heading` |
| ⑤ | STATE の進行中表が実態とずれる | 射影。手で書けば C7（sha256）が見つける | `test_v1_class_5_state_projection_has_no_hand_written_place` |
| ⑥ | 要望が「提案」のまま実現済み | note/decision と task を辺で結ぶ | `test_v1_class_6_request_linked_to_realizing_task` |
| ⑦ | 残日数が起算日ごと古くなる | 日付だけ持ち計算する（C8） | `test_v1_class_7_milestone_days_remaining_is_computed_not_stored` |
| ⑧ | 常駐を数えるか毎回悩む | resident の扱いは VIEW/active の定義1箇所 | `test_v1_class_8_resident_categorized_in_one_place` |

`test_v1_class_1_variant_decision_approved_but_still_waiting` は①の亜種（decision が裁定済みなのに待っている）を追加で検算する。`test_v1_classes_regression_guard_cannot_bypass_state_machine` は「状態機械を経由せず不整合を作れないこと」自体の回帰止め。

**引き換えに失ったもの**: v1で執事が自由に行える「状態欄に文章を書く」直接編集の速さ。CLI経由に一本化した分、コマンドを覚える手間が増えた（ADR-001 §13-#9 は `cli.py` の宣言的な冗長さを可読性の代価として許容している）。

### 3.2 Context Graph

**何を変えたか**: `node`（task/project/decision/agent/note/milestone）と型付き `edge`（`depends_on` `blocks` `part_of` `duplicates` `supersedes` `derived_from` `decided_by` `delegated_to` `relates_to` `about` の10種）を同じ SQLite に持たせた。`manor ctx <id>` が本体・1ホップ・`depends_on` の2ホップ連鎖・直近イベント5件を、文字数予算内で組み立てる（超えたら relates_to → 2ホップ → イベントの順に落とし、落としたことを明記する）。

**なぜか**: ADR-001 D2 は「専用グラフDBは使わない。1人1台ローカルなら JOIN 数本で足りる」。v1 は「行の集合」だけで、タスク同士をつなぐ辺を持てなかった（意見箱 I10）。

**根拠（実データ実測。inputs §E2、2026-09-02）**: v1の`QUEUE.md`/`PROJECTS.md`を`manor import-v1`で取り込んだ結果——

- node 241（task 185・decision 32・project 16・milestone 6）、**edge 303**（depends_on 55・decided_by 19・relates_to 48・part_of 181）
- unresolved 0（初回はdepends_on/decided_byの解決漏れがあったが、裁定を経て0に）
- `graph blocked` 0件・`graph stale` 0件・open decision 0件・`manor check` 問題なし（exit 0）
- **waiting/hold 状態のタスク11件のうち、機械可読なブロッカー（depends_onまたはdecided_by）を持つのは3件のみ**。残り8件はv1では自由文でしか待つ理由が書かれていなかった。v2の運用では`waiting`に`--note`が必須（C3）だが、**辺の無いwaitingを知らせる検査は未実装**（次項6の候補C10）
- **行ごとの突き合わせ**（`manor import-v1 --reconcile`。v1 の Markdown を再パースして DB と task/decision/project/milestone/依存を1件ずつ比較）: **1,873 項目一致・齟齬 0**（本番 `home/` に作った DB で 2026-09-02 実測）。日付の読めないマイルストーン 1 件は取り込み対象外（`notes` に記録）
- `manor active`の出力は8,138バイト。v1の射影（`store.py --active`、7,657バイト）とほぼ同程度——**起動コストはv1段階で既に射影化されていたので、v2の利得は「軽さ」ではなく「書き手が1つであること」**

**「Context Graph Engineering」への回答（I10）**: 主人は「同一タスクの重複」「前後関係」「Context Graph Engineeringという言葉」の3つを挙げていた。v2はこの言葉が指すものを固定の製品機能としてではなく、「必要な問い合わせを表す型付きの辺」として実装している——`duplicates`辺と`manor task dup`（重複を1コマンドで確定させ、srcをwithdrawnにする）、`manor graph dups`（タイトルの2-gram類似度で候補を提示するだけで判定はしない）、`depends_on`/`decided_by`による「ブロッカーが片付いたか」の自動判定。実データでの重複候補提示は取り込み直後には確認できておらず（`graph dups`の閾値運用は今後の実データでの検証が要る）、ここは実装はしたが実地の効果測定はまだ薄い、というのが現状の到達点。

### 3.4 常時ロード層の軽量化

| 項目 | v1 | v2 | 差分 |
|---|---:|---:|---:|
| CLAUDE.md | 12,657 B | 3,056 B | −76% |
| SOUL/POLICY/AGENTS/INTENT 計 | 43,651 B | 19,297 B | −56% |
| 起動時の射影 | 7,657 B（`store --active`） | 8,138 B（`manor active`、v1実データ185件取り込み後） | ほぼ同水準 |

v1のQUEUE.md（当時125KB→8.8KBに射影化）は外部レビュー提案1を受けて2026-08-29の段階で既に軽量化されていた（`03_design/タスクデータをDBにする.md` §4-1）。したがって射影の重さそのものはv1段階で解決済みであり、v2の起動時射影がv1と同程度なのは後退ではない。**v2で新たに得た利得は「読む量」ではなく「書き手が1つに定まったこと」**——v1は射影を読む側だけを変え、書き込みは依然手作業だったのに対し、v2はhookが書き込み経路そのものを閉じている。

### 3.5 委譲の型（handoff）

**何を変えたか**: `manor handoff new <task> --to <agent>`が指示書（役割とスコープ／背景／目的・今の状態・次の一手／Project Policy／制約／関連／成果物と置き場／検証要件／定型／報告の型、の10節）をMarkdownとDBの両方に生成する。同一トランザクションでtask.owner・status・delegated_to辺を更新する。報告は5見出し（やったこと／証跡／やっていないこと／曖昧だった点／主人にしか決められないこと）を必須とし、欠けていれば終了コード1で突き返す。

**なぜか**: 意見箱I8が記録した実例——「4通とも自然文で返ってきて、執事が読んでQUEUEへ手で書き写した」——には、読み違え・執事不在時に進捗が入らない・粒度がばらばら、という3つの穴があった。v1のAGENTS.mdは「委譲時に必ず渡すもの9点」を散文で定めていたが、機械が守る形にはなっていなかった。

**根拠**: `test_handoff.py::test_brief_has_all_ten_headings`が10節の生成を、`test_report_missing_headings_rejected`/`test_report_all_headings_accepted`が5見出しの必須化を検算する。`test_reject_returns_task_to_butler_on_hold`はreject時にowner・statusが戻ることを確認する。

**引き換えに失ったもの**: 部下が自然文で柔軟に書ける自由度。定型に沿わない報告は機械的に差し戻される。

### 3.6 境界の機械化

**何を変えたか**: v1で`00_butler/`・`tasks/`・`agents/*/data/`・`apps/*/_ops/`・`_inbox/`・`_master/`に散っていた②（主人の情報）を`home/`1箇所に集約し、`.gitignore`は`home/*`＋`!home/README.md`の2行で外す設計にした（v1は約15行が散在）。`tests/test_privacy_boundary.py`は`.gitignore`の内容を読むだけでなく、一時ディレクトリに本物のgitリポジトリを作り`git check-ignore`を実行して、②④に該当するファイルが実際に無視され①③に該当するファイルが実際に追跡されることを検算する。

**なぜか**: 「集約した」と書くだけでは守れない——実際にgitが無視するかを確かめる必要がある、というのが`tests/test_privacy_boundary.py`冒頭のdocstringの立場。

**根拠**: `test_gitignore_collapses_private_data_into_home`（設計の宣言を検算）、`test_git_actually_ignores_home_and_keeps_readme`（本物のgitでの実地検算）、`test_no_windows_user_paths_in_tracked_files`（`C:\Users\<誰か>`形式のパスが追跡対象に混ざっていないかを正規表現で検算）。**この試験の初回実行時、`ROADMAP.md`に混入していたユーザー名入りのWindowsパスを実際に検出した**（inputs §D）。試験を書いた効果が机上の空論でなく、実地で1件を捕まえた形で確認されている。

### 3.7 移植性

**何を変えたか**: v1の道具は`.ps1`36本・`.py`37本の混在だった（`butler-board`だけで18,896行）。v2は`src/manor/`配下をPython標準ライブラリ中心（sqlite3/argparse/tomllib）で統一し、ORMも使わない（ADR-001 D4）。リポジトリ内を`find . -name "*.ps1"`で検索すると、`.venv/Scripts/activate.ps1`（uvが生成する仮想環境の付属物で、追跡対象外）を除き0本。

**なぜか**: v1の`03_design/移植性の設計.md`規則2「新しく作る道具はPython（uv）」を踏襲。hooksも`python -m manor.hooks`で呼ぶ。

**引き換えに失ったもの**: Windows固有の処理（レジストリ操作やDPAPIなど）が必要な場面では、都度Python側で代替手段を探す必要がある。今回のcore実装ではそうした場面自体が出ていない。

## 4. 改善サイクルの実証

設計は「契約（ADR）→実装→曖昧だった点の申告→執事の裁定」という順で進んだ。実装役（Sonnet、6セッション）が挙げた曖昧点への裁定は、ADR-001 §13に10行、ADR-002 §9に17行、ADR-003 §8に12項目（本文9＋実データでの試し取り込み後の追補3）、**計39件**が記録されている（各ADRの該当節の行数を数えた実測値）。

代表例を3つ挙げる。

1. **`Path.write_text`の改行コード**（ADR-001 §13-#10）: WindowsではPythonの`write_text`が`\n`を`\r\n`に変換するため、射影ファイルのsha256がDB記録値と一致しなくなる不具合が実装中に見つかった。裁定は「`write_bytes(utf-8)`を規約にする」。v1でも同じ罠を踏んでいたと記録されている。

2. **`\b`の正規表現バグ**（ADR-003 §8-#3）: 対応表の原文どおり`\b[BQ]\d+\b`でv1のタスクID参照（`B2`など）を拾おうとしたが、PythonのUnicodeモードでは日本語の文字も`\w`とみなされるため、空白なしで隣接する日本語（`"B2の後に"`）では境界が成立せず取りこぼす。ADRの例文`"B88 の後に"`（空白あり）はたまたま拾えていただけだった。実装では`(?<![A-Za-z0-9_])[BQ]\d+(?!\d)`に置き換えて解決した。

3. **`handoff reject`後のowner**（ADR-001 §13-#5）: 却下された委譲のタスクをどう扱うか契約に明記が無く、実装役が申告。裁定は「ownerをbutlerに戻し、statusを`hold`、noteに却下理由を記録する」。据え置くと「委譲中」が射影に残り続けるため。

公開前の検分（`qa`）でも同じ型で2件が見つかった（ADR-001 §13-#11・#12）: 射影保護の hook が `home` という**フォルダ名**でしか判定しておらず `MANOR_HOME` を別名へ向けると素通りしたこと、`.githooks/pre-commit` を配線する手順が無かったこと。どちらも「命じてある」と「塞いである」の差で、検分役が実際に破りに行って見つけ、修正して試験を足した（`tests/test_hooks.py` の `MANOR_HOME` 解決3本、`tests/test_gitsetup.py` 3本）。

このほか、依存解決を1パスから2パスに分けた変更（前方参照の誤判定を防ぐため、ADR-003 §8-#4）、`content`欄からの言及を`depends_on`ではなく`relates_to`に張り替えた変更（ADR-003 §8-10、実データで確認された運用実態に基づく）なども、契約と実装のずれを執事が裁定して契約側に書き戻した例である。

## 6. やらなかったこと・限界・次の一手

**今回やらなかったもの**（inputs §F）: Webダッシュボード（v1の`butler-board`相当、18,896行）／Slack・Notion・カレンダーの実接続／夜勤（無人実行）／声・姿／判断待ちの声かけ／振る舞いの回帰試験。いずれも環境依存（④）か、別段として切り出す判断。

**次の一手の候補**:

- **C10（検査候補）**: waiting/hold状態で、depends_onもdecided_byも持たないタスクを知らせる検査。実データではwaiting/hold 11件中8件がこれに該当し、v1と同じく自由文でしか待つ理由が書かれていない状態が残っている（§3.2）。
- **振る舞いの回帰試験**: 外部レビュー提案5が指摘したとおり、docsにはpytestがあるが執事自身の振る舞い（曖昧な依頼への対応、HG該当時の停止など）を検証する試験は無い。v1設計文書`振る舞いの回帰試験.md`を継承候補として残している。
- **ダッシュボード・通知**: v1の`butler-board`相当の画面と、判断待ちの声かけは、どちらも環境（④）に依存するため今回は対象外にした。

**v1から移行するときの手順**: `manor import-v1`を本番の`home/`に対して実行する前に、必ず`--dry-run --json`で件数（node/task/decision/project/milestone/edge）と解決できなかった参照の一覧を確認する。取り込み直後は`manor check`がC1（ブロッカーが片付いたのに待っている）を検出する可能性がある——これは取り込み前のv1データに実際に存在した不整合であり、取り込みバグではない（ADR-003 §8-#9）。C1以外が検出された場合は取り込み処理を疑う。
