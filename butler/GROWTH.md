## G10 — 「試験は通っていた」で終わらせない（2026-09-05）

**観測**: 主人が実機で出した4件（小窓のヘッダ・ピン留め・Light/Dark・黒い窓）は、
どれも試験が通っている状態で起きた。さらにこの回だけで、実機を触って初めて見えた
ものが3つ増えた——初回保存だけ `chef = ""` が残る、PowerShell の書いた JSON が
BOM で弾かれる、関門が「①層の変更なし」と嘘に近い報告をする。

**仮説**: 試験は「呼んだら正しく動くか」を見るが、主人が触るのは**経路**である。
API を直接叩いて確かめて「直った」と報告したことが実際にあった（小窓のヘッダ。
API は直っていて、画面のボタンが古い開き方のままだった）。

**打ち手**: 主人に渡す前に、**画面のボタンから**辿る。API の応答ではなく、
ボタンを押して出た結果を見る。設定の類は**保存したあとのファイルの中身**まで見る
（「書けた」ではなく「余計なものが残っていないか」）。

**検証**: 今回は担当ごとの声を、使い捨ての home を立てて実際のブラウザで
拡張機能のカードから保存し、config.toml に1件だけ書かれること・同じ文でも担当
ごとに別の wav になることまで確かめた。`chef = ""` はこの手順で見つかった。

## G11 — 検算は「辞書」だけでなく「呼び出し」も見る（2026-09-05）

**観測**: 多言語対応で「訳の抜けは試験で塞ぐ」を機構にした。ja/en のキー集合の一致を
検算し、実際に訳を1つ消すと型検査と試験の両方が落ちることも確かめた。それでも実機で
画面に `undefined` が出た——**日本語側まで壊れていた**。

**仮説**: 塞いだのは「辞書に何が入っているか」で、「呼び出し側が正しく使っているか」は
見ていなかった。辞書は正しいので検算は緑のまま通る。**緑の試験が「無事である」ことの
証明にならない領域**が残っていた。

**打ち手**: 型を変え、差し込みが要る項目を引数なしで呼んだら `tsc` が落ちるようにした。
機構を作ったら「その機構が見ていない範囲はどこか」を明示的に問う。

**検証**: わざと引数を外して型検査が落ちること・戻せば通ることを実測した。残る限界
（引数の**名前**の取り違えは型で見ていない）も記録に残した。**塞ぎ切れていない範囲を
書かないと、次の人が「塞がっている」と誤解する。**

**併せて**: この後退は担当の報告では「全部 green」だった。**緑の報告と実機は別物**
（G10 と同じ）。画面を実際に開いて読むまでは、直ったとは言わない。

## G12 — 主人が一度直させたものは、機構で守る（2026-09-05）

**観測**: 主人が 2026-09-04 に「選択肢のラベルに絵文字は不要」と指示し、外した。その後
多言語化で辞書を作り直したとき、🐢🚶🏃 が**戻っていた**。実機のプロジェクト作成フォームを
開いて初めて気づいた。試験は全部緑だった。

**仮説**: 「一度直したこと」は記憶に頼っている限り必ず戻る。担当が代わり、ファイルが
作り直されれば、指示は文書の中にしか残らない。**文書は次の実装者が読むとは限らない。**

**打ち手**: 主人の指示のうち「こうであってはならない」という形のものは、**試験にする**。
今回は「主人が選ぶラベルに絵文字が入っていたら落ちる」を足し、絵文字を戻して実際に
落ちること・戻せば通ることまで確かめた。

**適用の目安**: 主人が2回言う前に機構にする。「前も言いましたが」と言わせたら執事の負け。

## G13 — 試験は「私の機械にたまたま在るもの」を読んでいる（2026-09-05）

**観測**: 公開後、CI で3回続けて落ちた。手元では毎回全部緑だった。

| 何を読んでいたか | 手元 | CI |
|---|---|---|
| `~/.manor/git-leak-terms.txt` | 在る | 無い → 送信前検査が fail-closed で 1 件失敗 |
| `home/config.toml` の `[manor] language` | 検証で `en` が入っていた | — |
| **OS のロケール** | 日本語 | 英語 → CLI の出力が英語になり 9 件失敗 |

**仮説**: 隔離したつもりで、隔離したのは「思い出した入口」だけだった。`MANOR_HOME`・
秘密の置き場・ショートカットの置き場は塞いだのに、**同じ性質の入口が3つ残っていた**。
「試験が読むもの」を列挙する目を持たず、失敗するたびに1つずつ塞いでいた。

**打ち手**: 塞ぐときは「この試験は外の何を読むか」を**列挙してから**塞ぐ。今回で言えば
——ファイル・環境変数・OS のロケール・タイムゾーン・プラットフォーム・ビルド成果物。
`tests/conftest.py` の docstring にそれぞれの理由を残した。

**検証の作法もひとつ**: 「直した」の確かめ方は、**逆を与えて落ちないこと**が強い。
今回は `MANOR_LANG=en` を外から与えて全体を回し、1535 件が通ることを見た——
「手元で通る」は何も証明しない（G10 と同じ）。

**残る限界**: 英語ロケールの Windows は手元に無いので、符号化とロケールの再現は
`locale.getlocale` の差し替えと、英語コードページでの実測に頼っている。
**CI が最後の検分**という状態は変わっていない。

## G14 — 「やりました」の前に、返り値を見る（2026-09-06）

**観測**: v1 から v2 へ切り替える日、`manor night install --at 02:00 --yes` が
「登録しました」と言った。実際には schtasks が終了コード 2147500037 で落ちていて、
**タスクは1本も登録されていなかった**。気づいたのは、たまたま `Get-ScheduledTask` で
確かめたからで、確かめなければ**今夜の夜勤が動かない**まま朝を迎えていた。

**なぜ起きたか**: `install()` は `subprocess.run` の結果を辞書へ詰めていたが、
`returncode` を**誰も読んでいなかった**。CLI は `result["executed"]`——「実行を試みたか」
——だけを見て「登録しました」と表示し、終了コード0を返していた。**試したことと、
できたことを、同じ言葉で言っていた。**

**打ち手**: `install` / `uninstall` の結果に `ok`（真偽）を持たせ、CLI は失敗なら理由と
終了コード1で止まる。あわせて `/TR` の中の `"` を逃がした（落ちていた直接の原因は、
リポジトリのパスに空白があること）。

**一般化**: これは夜勤に限らない。**外の何か（OS・API・別プロセス）に頼んだ仕事は、
頼んだことと済んだことが別。** 執事が「送りました」「登録しました」「消しました」と
言えるのは、**返り値か、外から見た実物か、どちらかを確かめたときだけ**。
今回は `Get-ScheduledTask` で実物も見た——両方見るのが一番強い。

**残る限界**: 同じ形が `manor shortcut create` や `manor web install` にも在りうる。
今回は数えていない（数えるべきだが、切り替えの当日に手を広げないことを選んだ）。

## G15 — 起動口が2つあるものは、片方だけが使われている（2026-09-06）

**観測**: `--sleep-back` を `manor night` 側に足し、試験も19件書いて全部緑にした。
そのあと**登録したコマンドをそのまま手で叩いてみたら**、`python -m manor.night run
--sleep-back` が `unrecognized arguments` で落ちた。夜勤の起動口は2つあり、
**スケジューラに登録されているのは試験していないほう**だった。叩いてみなければ、
翌朝「夜勤が丸ごと動かなかった」で気づくことになっていた。

**なぜ起きたか**: `__main__.py` が引数の定義を**書き写していた**。しかもその docstring
には「同じ dest 名を使い、二重に書いて食い違わせない」と**書いてあった**——
散文で「食い違わせない」と誓っても、食い違いは防げない。v1 README が
「機構は散文では守られない」と言っていたのと同じ形を、自分でもう一度踏んだ。

**打ち手**: `__main__.py` は `_add_*()` を呼ぶだけにした。`notion.py` も同じ形
（`register()` と `main()` の書き写し）だったので、共通の組み立てに寄せた。
そのうえで**2つの口が同じ引数を受けることを試験にした**
（`tests/test_night_entrypoints_agree.py`）——書き写しが戻ってきたらそこで落ちる。

**一般化**: **同じ機能に入口が2つあったら、片方は必ず腐る。** 腐るのは、使われて
いないほうではなく**試験されていないほう**で、その2つはたいてい一致しない。
今回は「実運用が叩くほうが、試験の無いほう」という最悪の組み合わせだった。
入口が2つある機能を触ったら、**登録・配線されている側から叩いて確かめる。**

⚠ **試験の側で引数を書き写さないこと。** それをすると「試験と実装が一致している」
ことしか言えず、肝心の「2つの入口が一致していること」は何も言えない。今回いちど
その形の試験を書きかけて、気づいて捨てた。

**残る限界**: `manor slack` / `manor notion` は今回そろえたが、`board` にも同じ
2つ口の形がある（`register()` と `__main__.py`）。数えていない。

## 2026-10-02 — 「再現しない」で止めず、手段を変える（外部視点 E41・採用）

**観測**: T96（全体試験でだけ落ちるflaky test）は2026-09-24から6晩越え、毎晩「全体で実行→非再現」を繰り返すだけで止まっていた。nextも「pytest-randomly等で並び順を変えて多数回回す」止まりで、具体的な次の一手になっていなかった。

**外部の視点**: `pytest-randomly` は失敗時のシードを記録し`--randomly-seed=last`で再現できる。`detect-test-pollution`（asottile）はテスト対をビセクションして汚染源そのものを特定する専用ツール。「疑って手探りで何度も回す」と「再現したシードを記録し汚染源を機械的に特定する」は別の強さの手段。

**打ち手**: T96のnextを「pytest-randomlyを導入し失敗時のシードを記録→detect-test-pollutionで汚染源のテスト対を特定する」に具体化した（`manor task set T96`）。

**観測条件**: 次にT96へ夜勤か昼の執事が着手するとき、この2点セットを実際に使ったか、使わなかったなら理由が書かれているかを見る。使って再現できたか特定できたかが「効いた」の判定基準。
